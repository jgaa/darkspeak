# DarkSpeak VFS Composition

## 1. Role

Implement an application-layer VFS that assembles namespaces provided by `IFileManager` into identity-specific virtual directory trees. The VFS is **composition, not another storage engine**: it delegates storage operations to FileManager and never indexes/hashes physical files itself. Multiple identities can mount the same application-wide read-only namespace, sharing its index/cache. Identity-owned writable managed namespaces remain distinct. The VFS layer knows identity/mount ownership; remote access policy belongs to the separate authorization module, which filters each requesting contact's view.

## 2. Mounts and identity

Persist each identity's mount records with stable opaque IDs, source `NamespaceId`, source directory ID (usually root, optionally a subtree), virtual parent/path/name, and presentation settings. Changing a virtual mount name or parent does not change source IDs or require rewriting descendants. Resolve `(identity, virtual node)` to an explicit `(mount, namespace, FileId/DirectoryId)` tuple; never use peer-supplied physical paths. Expose opaque VFS node IDs scoped to an identity/mount; identical source objects appearing through different mounts are distinct virtual entries but share the same backend content/index. Avoid ID collisions and cycles, including nested mounts and source aliases.

The composed root and virtual mount nodes may be synthetic. Validate mount overlap, conflicts, renames, nesting, and removal transactionally. Reject mount names that collide with existing children; do not shadow either entry. If an external filesystem change later creates a collision, make the ambiguous name inaccessible until the conflict is resolved. Discovering such a conflict must create a notification in the application's Home pane identifying the affected virtual location and explaining that the conflict needs resolution. Coalesce repeated reports of the same unresolved conflict within bounded notification state. Conflict details are local administrative information and must not expose hidden source objects to remote contacts. A VFS instance is lightweight derived state reconstructed from persisted mounts and FileManager catalogs. Cache mount resolution without duplicating complete per-file metadata. Mount configuration changes invalidate affected derived views with generations.

Derive opaque source-backed VFS node IDs from the identity, stable mount ID, source namespace ID, and backend object ID using a persisted secret and a versioned, unambiguous encoding. Use a cryptographically sound keyed construction with domain separation from synthetic node IDs; do not persist a per-file ID mapping. Ordinary mount rename/move preserves node IDs. Deleting and recreating a mount assigns a fresh mount ID and therefore fresh node IDs. A new backend object ID produces a new VFS node ID and must not inherit permissions attached to the previous object. Synthetic directories use persisted UUIDs. Persist the derivation secret across restarts so unchanged mounts and source objects retain their IDs.

A subtree mount grants access only within its configured source directory subtree. Validate subtree membership for every resolved source object and mutation endpoint; knowledge of a backend ID does not grant access to ancestors, siblings, or other objects outside that subtree. Revalidate membership when source topology changes. Under `WithinVfs`, an alias leaving the subtree requires an independently authorized destination mount. `Always` adds only the assignment-authorized external regular-file exception defined in §5.

### 2.1 Storage registry and assignments

Persist versioned storage resources (stable resource ID, namespace ID, read-only/shared or identity-owned writable ownership) and identity assignments (stable assignment ID, identity, resource, permitted directory ID, explicit external-regular-file capability). Runtime backend registrations do not grant read-only access. Multiple writable resources may belong to one identity. Ownership and assignment restrictions are validated on mount creation, every use, aliases and mutation endpoints, independently of contact/group permission callbacks. Source ancestry is established using stable catalog IDs, never physical paths. Administrative updates advance a registry generation; request contexts and delegated operations retain it, and withdrawal revokes readers, subscriptions, writers and commit authority. Serialize updates against active commits. No lower tier can expand an assignment or backend exclusion.

### 2.2 Effective topology

Persist mount definitions separately from request-bound derived topology. Definitions retain identity, stable mount ID, assignment/source, absolute logical placement, tier (identity/group/contact) and principal/provenance. Request groups are trusted identity-scoped host input. Compose identity, then applicable groups, then contact definitions, using tier precedence before path specificity. Incompatible group sources at the same path produce an inaccessible conflict and a bounded coalesced local Home notification; never resolve by iteration order. A higher-tier replacement at a path shadows the inherited subtree, including lower-tier descendant mounts; definitions at the replacing tier can reintroduce descendants. A contact replacement wins over group mounts. Permission-only rules do not alter topology. Synthetic navigation ancestors have stable opaque IDs and reveal no underlying denied source contents. Effective views are disposable and bound to identity, contact, configuration and authorization generations. Provenance is retained for local administration/View as Contact, never leaked accidentally through remote metadata.

### 2.3 Permission resolution and navigation

Resolve each permission contact → merged groups → identity. At each tier, consider the most specific applicable logical path rule with a specified value; `UNSPECIFIED` continues inheritance. Resolve each group independently before merging: `DENY` wins, else `ALLOW`, else `UNSPECIFIED`. Identity defaults give definitive decisions. A deeper group rule cannot override an applicable explicit contact denial. Path-level `DENIED` blocks the subtree unless a higher-tier explicit grant reopens the requested path. Reopened children may establish navigation-only ancestors without listing underlying source contents. Distinguish virtual navigation, source `RECURSE` and subtree denial. `RECURSE = DENY` suppresses ordinary source subdirectories, not direct files or independently authorized child mounts. Authorization remains mount/context scoped; the shared backend stores no requester policy.

## 3. Common operations

Provide async, paginated browse/lookup/stat, source-aware directory subscription, and read preparation by delegating to `IFileManager`. Preserve FileManager error, cancellation, cursor/generation, and capability semantics; map source identifiers to stable virtual identifiers. File operations on writable mounts delegate to the managed backend after VFS authorization; read-only mounts expose their backend's read-only capabilities. Do not implement a parallel copy/resume/commit engine. FileShare downloads use `prepareRead` so the caller obtains the SHA-256 and matching prepared reader before streaming any bytes.

Reject ordinary directory moves/removals when the directory contains nested mounts; the user must explicitly move or remove those mounts first. Explicit virtual mount moves remain mount-configuration operations. Reject cross-mount file/directory moves even when both mounts use the same backend namespace; copying uses the existing transfer workflow.

Compose directory listings from backend entries and effective child mounts using one deterministic name/ID order. Inspect only a bounded number of backend candidates per request, apply shadowing/authorization before emitting, and return an opaque continuation whenever work remains, including empty pages. Retain bounded enumeration state; never restart an expensive filtered scan on every page or construct a whole million-entry filtered directory before returning its first page. Cursors bind effective topology, identity/contact, policy/assignment generations, directory, presentation and relevant catalog state. Backend invalidation is handled internally with bounded recovery and no visible hidden-only generation signal. Catalog export still stages a complete per-directory-consistent artifact before transfer. Do not build an unbounded full in-memory tree to answer one listing. Preserve cached old metadata and `Updating` state; block read preparation while an entry is stale. A directory subscription to a virtual node owns a move-only `DirectorySubscription` for the underlying directory plus VFS mount-change interest. Only subscribed directories are pinned/receive detailed notifications; source events are mapped into virtual generations. Subscriptions must survive ordinary virtual rename/move through stable node IDs and terminate cleanly when mounts disappear.

## 4. Authorization boundary

VFS composition identifies candidate objects but **does not itself grant peer access**. All remote listings, metadata, thumbnails, read preparations, VFS exports, and mutations pass through the same contact authorization component. Check visibility of both parent traversal and requested operations; hidden entries must not affect visible counts, timestamps or snapshot generations. Permissions are derived from identity defaults, contacts, and groups in the authorization spec, not stored in the FileManager catalog. Reauthorize at use time: cached listings and remote catalog snapshots are never authority to read.

Authorization is mount-scoped: evaluate each operation for the requesting contact against `(identity, mount, source object ID, operation)`, including the namespace identified by that mount. The same backend object may have different permissions through different mounts. A grant through one mount never authorizes access through another. Request-owned adapters to backend authorization callbacks retain the selected identity/mount context throughout delegation; a bare `(namespace, source object ID)` is insufficient authority. Cross-mount alias resolution explicitly selects and authorizes the destination mount while preserving authorization checks on the exposed link/path.

Remote views use contact-visible revisions and authorization-filtered notifications; backend generations remain internal. Changes affecting only hidden entries must not change exposed directory counts, timestamps, revisions, snapshot generations, or notifications, nor cause externally observable cursor invalidation solely because an internal backend generation changed. Apply the same filtering to synthetic and source-backed directory metadata. Backend cursor invalidation must be handled internally while preserving the visible pagination contract. Authorization changes still require reauthorization and may invalidate the affected requester's cursors. These guarantees cover explicit metadata and protocol signals; eliminating timing side channels is outside this specification's scope.

Reauthorization covers active operations as well as admission: retain request-owned mount and authorization context for prepared readers, subsequent reads, subscriptions, pending writers, and commit. Mount removal or permission withdrawal revokes affected handles, stops readers/subscriptions, blocks further writes, and prevents pending commits. Recheck authorization at the commit boundary and serialize revocation against that boundary so a revoked operation cannot subsequently publish a commit. Snapshot/resume leases remain bound to the authorized identity/mount context and cannot bypass current authorization. Already transmitted bytes and completed commits cannot be recalled.

## 5. Symlinks

Preserve backend policy `Never` / `WithinVfs` / `Always`, with `Never` the default. For `WithinVfs`, resolve the final target to a VFS-represented object and require authorization for both the exposed link/path and the target as seen by the requester; cross-mount links use explicit mount resolution. `Always` behaves like `WithinVfs` for directories and independently accessible files. It additionally allows final external regular-file targets only when the backend is configured `Always` and the selected identity assignment explicitly permits external files. An assignment restricted to a subtree never inherits this capability implicitly. Final-target type, exclusions, opened-object identity, bounded chains and active revocation are enforced by the backend; intermediate directory symlinks do not become independently browsable. Both policy controls require the red file-only warning in `agents.md`. Directory aliases delegate to the selected destination and do not duplicate indexing.

## 6. Local/remote consumers

The local Dolphin-like browser uses the same VFS browse/read/write contracts as the FileShare server, with source capabilities controlling UI affordances. The remote VFS presents a host-neutral UNIX-like `/` hierarchy, with typed plain-UTF-8 or canonical ASCII-percent-escaped paths. Presentation labels are virtual, not native OS paths; special logical filenames such as `CON` remain unchanged to peers. FileShare wire representation and native-materialization mapping are specified separately in `ftp/fileshare_protocol.md` and `ftp/fileshare_server.md`. Remote recursive catalogs are versioned, bounded **authorization-filtered** snapshots of one contact's visible VFS metadata; optional thumbnails are a separate bounded payload. A cached remote catalog can support lag-free browsing but is only historical metadata, not a capability grant. Actual downloads reauthorize and bind to current expected SHA-256/content. Dragging remote objects to the OS uses the existing transfer engine and local materialization; dropping into writable managed mounts uses FileManager creation/verification. Cached catalogs, queue/history views, and tag filters are consumers, not part of VFS storage.

### 6.1 Initial catalog export and transfer

**Direct nonrecursive remote directory listings** use the existing bounded paginated `Vfs::list` operation, exposed as FileShare `LIST` requiring ordinary LIST permission on the selected directory; no EXPORT or RECURSE permission is needed to inspect its immediate authorized children. **Recursive remote listings** are a distinct, server-optional request: the server must explicitly approve or refuse recursion before enumeration. A refusal sends no listing entries, counts, partial catalog, metadata or artifact offer; the peer may retry with nonrecursive LIST requests directory by directory. Approved recursion uses a staged catalog export carried by the existing generic file-transfer protocol (`protocol.md`). Initiating that export requires explicit EXPORT and LIST permission at the requested root, and every included entry and traversed directory must independently satisfy LIST, RECURSE, path-denial, assignment and exclusion checks. See `ftp/fileshare_server.md` and `ftp/fileshare_protocol.md` for wire-level behavior. EXPORT never exposes data hidden from ordinary authorized browsing. Backend pagination is an internal generation mechanism, not the remote transport contract. Generate a private temporary export through the optional common `IFileManager` temporary-artifact capability in bounded asynchronous batches, authorizing traversal and each emitted entry. Select a supporting backend explicitly (it may be an identity-owned writable namespace); if unavailable or its temporary budget is exhausted, fail with a typed error rather than persisting the export as a normal visible VFS file. Records contain virtual node/parent IDs and permitted presentation metadata, never physical paths or private backend identifiers. Use a versioned format with regression fixtures and explicit bounds on record size, entry count, recursion depth, total bytes, and generation time. Bound traversal state and detect alias/mount cycles. If limits prevent completion, return an explicit failure and allow a smaller subtree request; never present a partial export as complete.

The initial implementation stages the complete export, finalizes its size and SHA-256, and then offers it as immutable content. Reuse the generic transfer engine's existing chunk window, ordinary flow-control acknowledgements, **mutually verified durable SHA-256 checkpoints**, sender-selected resume positions, integrity verification and cancellation, without catalog-entry acknowledgements or a second transfer engine. Catalog exports, thumbnails and preview images transferred in either direction are exempt from exchange-credit awards/debits, but not authorization, concurrency or storage limits. The receiver validates the complete export and its format before atomically publishing it as a cached catalog. Exports are historical browse results with per-directory consistency; they do not promise a single atomic point in time across mounts/databases. Release database queries/transactions between generation batches and before waiting for the receiver. Source updates must not silently produce an internally inconsistent directory result; retry boundedly or fail generation when necessary.

Catalog transfers share the existing per-contact transfer allowance (currently two active transfers per contact connection). Add explicit per-contact, identity, backend and shared-physical-pool admission limits covering export generation and transfer, bounded queues, independently accounted temporary/cache quotas, reservation budgets, idle timeouts, and export lifetimes; preserve capacity for permanent data, incoming staging and recovery. Limit concurrency initially rather than adding a complex scheduler. Generation, hashing, parsing, and validation yield between bounded worker batches, remain cancellable, and never block the UI thread. A stalled receiver cannot retain export resources indefinitely. Authorize generation, offering, active transmission, and resume against the current requesting contact and identity/mount context; cached export possession grants no access.

### 6.2 Future immutable export caching

Caching is a future optimization, not required for the initial implementation. Read-only mounts may reuse cached listing content for requests with the same virtual mount/subtree, effective permissions, presentation rules, and compatible revision state. Equal permission labels alone are insufficient: cache reuse must preserve identity/mount-scoped node IDs and the exact authorized view, including traversal and alias-target decisions. Revalidate authorization on reuse; requester-specific metadata must not leak through shared cache content. Detected changes invalidate affected cache dependencies without exposing hidden-only activity.

Retain permitted old metadata for changed/unvalidated entries and overlay `EntryStatus::Updating` until revalidated. This preserves browsing while blocking new content reads/preparations for those entries. Patching status cannot retain newly forbidden/excluded objects or ambiguous conflict entries; omit them and apply revocation immediately. Cache reuse never weakens current access checks or backend freshness requirements.

A future composed reader may present an imaginary file assembled from immutable cache files and bounded in-memory patches. Freeze the exact ordered bytes, patch set, and referenced cache-file versions, then compute the complete size and SHA-256 before offering that representation. Pin those versions for active readers/resume leases; reads, retransmission, and resume must reproduce the same bytes. New cache generations use fresh unique filenames and never modify an offered generation in place. Bound patch memory, retained versions, storage, and lease lifetimes, and reclaim unreferenced versions safely. This remains a metadata-export reader feeding the existing transfer engine, not another storage or transfer engine.

## 7. Tests

Cover mount-name collision rejection, external filesystem changes creating conflicts, inaccessible ambiguous names, Home-pane notification delivery and coalescing, conflict resolution, nested-mount move/removal rejection, and cross-mount move rejection within a shared namespace.

Test mount removal and permission withdrawal during prepared reads, subsequent reads, subscriptions, pending writes, and commit races; verify snapshot/resume leases cannot bypass revocation or be reused through a different mount context.

Test single-directory and recursive multi-mount exports, per-directory consistency under concurrent updates, explicit limit failures without partial publication, bounded generation/transfer admission and storage, stalled-receiver cleanup, existing transfer-window backpressure and resume, format fixtures and hostile record parsing, and revocation during generation/transmission/resume. When future caching is implemented, test view-compatible reuse, hidden-change privacy, `Updating` overlays, immediate exclusion/revocation, and byte-identical hashed composed readers while new cache generations are published.

Test sharing one backend between multiple identities without duplicate indexing; mount/subtree aliasing and virtual moves; subtree confinement against guessed backend IDs, outside-subtree mutation endpoints, and source topology changes; different permissions for the same source object through different mounts without grants leaking between them; synthetic listings/pagination; stable IDs across restart and mount rename/move, fresh IDs after mount recreation or backend object replacement, and versioned ID derivation regression fixtures; generation invalidation; permission-filtered views and snapshots; hidden-only changes leaving exposed counts, timestamps, revisions, notifications, and cursor validity unchanged; cross-mount symlink authorization vs insecure `Always`; subscriptions/pin lifetime during mount removal; concurrent backend updates; namespace isolation; and low-memory browsing of large collections. Keep the VFS independent of any concrete FileManager implementation.

Regression cases additionally cover persistent assignment ownership/restrictions and withdrawal; tier/path permission inheritance and group deny merging; group mount conflicts, contact replacement and inherited-subtree shadowing; explicit mounts below nonrecursive/denied parents; navigation-only reopening; bounded empty-page continuation; and file-only `Always` with assignment opt-in and alias/exclusion/revocation checks.
