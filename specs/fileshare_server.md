# DarkSpeak FileShare Server — initial remote read service

**Status:** Initial implementation contract. **Companion:** `fileshare_protocol.md` (wire objects and state transitions). This document owns server behavior; `vfs.md`, `fileshare_authorization.md`, `file_manager.md`, `read_only_file_manager.md`, and `protocol.md` remain authoritative for their respective subsystems. No second filesystem, identity model, or transfer engine.

## 1. Goals and boundaries

Expose each local identity's explicitly assigned, authorized virtual filesystem to authenticated DarkSpeak contacts, with **UNIX-like virtual paths** regardless of the server's host OS. Serve direct directory listings, optional server-approved recursive catalog listings, metadata and ordinary-file downloads. Keep private physical paths, backend types, OS behavior, source IDs, hidden metadata, and authorization policy confidential. All peer input is hostile even for approved contacts. Use bounded asynchronous operations and preserve immediate UI responsiveness.

The server is a feature-specific controller over the existing per-application VFS and generic coroutine-owned `TransferManager`. It may request a generic transfer, but never implements file chunking, hashing, checkpoints, resume, channel scheduling or publication. No HTTP or independent FTP/TCP server; all requests travel inside the existing authenticated encrypted DarkSpeak protocol.

**Initial remote service:** capability discovery, path-based LIST/STAT, recursive listing request with explicit approval/refusal, catalog export delivery, GET/download initiation, request cancellation and optional directory subscriptions if already supported by the VFS. **Deferred to separate specifications:** remote upload/mkdir/rename/delete and quota/credit settlement, persistent user-visible queues/history, full remote browser UX, tags/ratings, distributed libraries and cross-contact cache optimization. Their wire operation numbers remain unassigned until specified.

## 2. Identity, request context and virtual namespace

- Bind every operation to the authenticated local identity, remote contact, connection, feature purpose, and current authorization generation. The authenticated session establishes requester identity; peer-provided identity/path fields never select another local identity or override the bound contact.
- Construct the effective VFS with existing identity default + group + contact mounts, rule precedence, source assignments, exclusions and selected symlink policy. The administrator's `View as Contact` must use the same evaluator, not a simulated approximation. The effective root is `/`, including synthetic navigation directories.
- Externally, the namespace has UNIX-like directory semantics: one leading `/`, `/` separators, ordinary path components, file/directory types and opaque stable virtual node IDs. Never expose drive letters, UNC paths, backslashes as separators, `\` filesystem roots, volume/device names, Windows attributes, Linux inode/mount IDs, macOS resource forks, native symlink targets, host paths, native API errors or backend provenance.
- A remote `VirtualPath` is the sequence of **VFS logical presentation components**, not an OS path. Resolve it stepwise from the authorized VFS root through `lookup()`, with authorization and mount context on every step. No string concatenation into native paths, URL-parser dispatch, `.. ` normalizing, or native filename sanitization before authorization. A path or returned opaque node ID is never authority.
- Both Unicode and ASCII-escaped path forms are defined by `fileshare_protocol.md`. Use the existing VFS `Request::allow_utf8` and established ASCII presentation rule. When **either** peer's effective security preferences require ASCII, use only the ASCII-escaped form for all names/paths and catalog labels. Otherwise UTF-8 paths may be used. Do not silently reinterpret one encoding as the other. A new connection re-evaluates policy; data learned under prior preferences cannot bypass current restrictions.
- Use stable virtual IDs for efficient follow-up requests and alias disambiguation where helpful, but accept paths as the normal client API. Node-ID validation is scoped to the identity, requesting contact's current view, mount and generation. A stale ID returns the same non-disclosing outcome as an inaccessible object.

## 3. Portable logical names and host-independent storage

The peer sees the same logical filename regardless of its own or the server's OS. The virtual namespace accepts ordinary UNIX-like names, including names such as `CON`, `AUX`, `NUL`, `COM1`, `LPT1`, and names containing characters reserved by Windows. These names are **not** rejected solely because of the host OS. Portable protocol restrictions are explicit and identical everywhere: no empty components, `.`, `..`, `/` within a component, NUL, invalid encoding or control/format code points not represented by the established escaped source-name policy. Enforce common length/uniqueness rules regardless of host, and respond with generic policy errors for actual logical conflicts rather than OS-specific errors.

Physical managed storage stores file content under opaque locally allocated names/IDs and retains the **exact VFS logical name** in its catalog. A host-specific materialization/export adapter performs reversible logical↔physical-name mapping when a native public path is explicitly required; otherwise no native filename is necessary. On Windows, never create or open a device alias such as `CON` using the peer's original name. On case-insensitive or normalization-constrained hosts, the catalog is the authority; physical aliases must not merge or overwrite distinct logical objects. Failure of an optional explicit native export is not grounds for rejecting a valid remote logical name or modifying the peer-visible name.

**Required follow-up to existing backend contract:** `file_manager.md` currently defines a managed-native logical-name policy rejecting Windows device names and other Windows-forbidden characters. That restriction **conflicts** with the host-neutral virtual namespace. The FileShare server must not work around it by silently renaming visible remote objects. Before implementing remote uploads or managed file creation, revise/version the common managed logical-name policy and add an opaque physical-name mapper/adapter with regression fixtures. Existing read-only source-name encoding `encodeLinuxName` remains distinct and unchanged. The server must not claim end-to-end write support until this contract is reconciled.

Host metadata is mapped into one fixed privacy-reduced portable schema: `FILE`/`DIRECTORY` only; no disclosed OS-specific special-file types. Non-regular objects are not remotely downloadable or traversable. A user wishing to transfer filesystem-specific artifacts (e.g. macOS metadata, device nodes or directory trees with special attributes) must package them explicitly, e.g. with tar, as ordinary file content. Do not implicitly expose extra streams, ACLs, xattrs, ownership, execute bits, link destinations, sparse layout, native filesystem allocation or OS fingerprints. File mtimes use the existing coarse VFS presentation (UTC day precision); directory timestamps/revisions are derived only from visible authorized content. Error mapping, limits, caps and name rules must not reveal the host OS. This is an explicit-metadata guarantee, not a claim to eliminate timing fingerprinting.

## 4. Requests and authorization

- Require peer-authenticated accepted contact status, a negotiated `fileshare-v1` feature capability, accepted security preferences, and feature-enabled identity configuration before dispatch. No legacy feature fallback. Requests are strictly correlated, typed and bounded; malformed shapes fail before application dispatch and serious protocol violations close the connection.
- `LIST` one directory requires authorized path traversal and `LIST` on the requested directory. Enumerate **only its immediate children**, in bounded pages using VFS cursors; filter unauthorized descendants and aliases. Does **not** require `EXPORT` or `RECURSE` and does not imply permission to inspect/download child content.
- A `LIST` request with `recursive=true` is a **separate optional operation**, never inferred from the normal listing. Before any enumeration, staging, catalog generation or response containing file metadata, the server decides whether to approve recursion based on configured `EXPORT`, `LIST`, `RECURSE`, policy, runtime quotas and local operator restrictions. It may **reject even if permissions otherwise allow**. On rejection, send only a generic refusal status with the matching request ID. **Send no entries, counts, partial pages, previews, names, hidden-path hints, prepared artifact or transfer offer.** Client can retry the same root with `recursive=false`, then explicitly request permitted subdirectories one at a time.
- Approval of recursive listing is **scoped to that request, root, contact and current policy generation**; it is not approval of subsequent downloads or a lasting right to recursive enumeration. During approved traversal, filter every entry and subdirectory using ordinary LIST/RECURSE/path rules, symlink/exclusion and assignment checks. Unauthorized subtrees are omitted, including their contents; explicit independently authorized child mounts may still be represented under existing VFS navigation rules. Limits, revocation, stale generation or errors abort generation and yield a **failure without a partial catalog**. Do not downgrade an approved recursive request to a nonrecursive result without indicating it.
- `STAT` requires relevant traverse/inspect permission and returns only authorized fixed-schema fields. `GET` requires current READ/DOWNLOAD on the exact resolved node and alias/mount, valid regular-file source, authorized content representation, current hash/size source evidence, storage capacity and generic transfer slot admission. A visible catalog name or node ID never grants download rights.
- For subscriptions, check LIST and applicable visibility per changed entry, use contact-visible revision/digest (not backend generations), and bound retained subscriptions and notification rate. Notification loss signals refresh, never exposes hidden counts or paths.

## 5. Directory listing transport

**Nonrecursive:** `ListDirectoryRequest(recursive=false)` produces `ListDirectoryResult` with a fixed small authorized page, opaque continuation and `complete` indicator. Page size and scan budget are independently bounded. An empty page with a continuation is valid. The cursor is opaque, scoped to the requester, directory, permission/presentation generation and expiration; a stale cursor fails safely. Never collect or sort an entire huge directory before the first page. Use the stable VFS ordering and existing bounded page API. Entries are returned in the selected path presentation encoding, with opaque virtual IDs for efficiency. No physical or hidden counts.

**Recursive:** `ListDirectoryRequest(recursive=true)` either returns a single refusal/error with **zero listing data**, or returns an accepted result referencing an immutable **staged authorization-filtered catalog artifact**. The server invokes the existing `Vfs::exportCatalog(identity,node,true,request,...)`, with its per-directory consistency, limits and resource leases. When staging and SHA-256 verification complete, offer the artifact through the existing generic checkpointed file-transfer engine using trusted local purpose `CatalogExport`; do not invent per-entry ACKs, another streaming protocol, or a new file engine. The accepted result includes the correlation/transfer identity and catalog format version; the actual catalog bytes travel only in the generic file transfer. If export staging fails, return an error and no partial artifact or result that looks complete. A refusal before staging must create no export.
 
The existing VFS export contract in `vfs.md` currently states all remote listings use staged catalog exports and require EXPORT. This document deliberately **refines it**: bounded single-directory LIST uses direct pages and LIST permission; recursive bulk catalog export uses EXPORT plus LIST/RECURSE and server approval. Update the `vfs.md` cross-reference consistently; keep exportCatalog's interface and contracts intact.

Client receives and validates catalog bytes with the existing `Vfs::validateCatalog` or equivalent bounded validator before publishing its cached view. Catalog contains historical metadata only. Per-directory consistency is required; a global atomic view across independently changing mounts is not promised. A catalog transfer is uncharged in both directions but consumes ordinary transfer and temporary-storage budgets. Catalog temporary artifacts use private leases with bounded cleanup and are never listed or mounted.

## 6. Download initiation

`RequestDownload` includes a virtual path or previously returned virtual node ID with matching contact/view context, plus optional expected content SHA-256/size/version to prevent downloading a silently changed object. Resolve and authorize against the current VFS, prepare an authenticated reader bound to that exact object/version with `prepareRead`, then create a generic outgoing transfer through the existing FileManager adapter and app-wide transfer manager. The server chooses a locally valid immutable transfer ID. Return a correlated decision/transfer ID; actual `FileOffer`, acceptance, checkpoint confirmations and resume follow `protocol.md` unchanged.

The feature controller retains the local identity, contact, authorized mount/source binding and trusted `FileShareDownload` purpose for the transfer lifetime; reauthorize on admission, preparation, subsequent read, reconnect and resume. No peer-supplied MIME, path, credit exemption, source ID or transfer ID overrides this trusted context. Do not send data after permission withdrawal. A cancellation of the *request* before transfer admission is not an implicit deletion of an already completed transfer.

Explicitly distinguish `VFS view path` from `generic FileOffer.name`: the transport filename is bounded portable display metadata and may be an escaped/shortened suggestion; it does not redefine the full VFS logical name. The client retains the original logical path/node metadata separately.

## 7. Limits, privacy and failure handling

All caps are locally configured or hard bounded: request bytes, depth/components, concurrent in-flight requests, per-contact and global browse/STAT rates, per-request backend candidates inspected, cursor count/age, subscription count, export generation/time/bytes/entries, retained temporary artifacts, active generic transfers and shared physical-pool quotas. Start from the `dsvfs::Limits` defaults; do not multiply them into unbounded queues. Apply control-traffic priority and backpressure. Use coroutine-based, cancellable operations; do not hold DB transactions during network waits. Admission limits for catalog generation and sending count together where specified.

Map backend failures to stable generic feature statuses (`DENIED_OR_NOT_FOUND`, `RECURSION_REFUSED`, `INVALID_REQUEST`, `STALE_CURSOR`, `BUSY`, `UNSUPPORTED`, `CHANGED`, `INTERNAL_ERROR`), never native errno/Win32 codes or physical file attributes. Authorization denials and absent entries share one public error. `RECURSION_REFUSED` is permission-policy-neutral; it contains no reason, hidden count, quota, alternative path or disallowed mount evidence. Even when the peer is denied, no user paths or sensitive values enter logs by default. Output only authorized metadata; generic server capability declarations cannot expose the host OS.

## 8. Implementation slices and acceptance

1. Wire schema/capability/codec validations from `fileshare_protocol.md` and feature dispatch with strict limits, no file-work logic in Peer.
2. Nonrecursive path resolution/STAT/LIST using `dsvfs::Vfs` and current authorization. Add deterministic pagination and ASCII/UTF-8 fixtures.
3. Explicit recursive approval/refusal, staged catalog export and checkpointed delivery using the existing transfer adapter. Guarantee no emitted listing data on refusal or failed export.
4. GET/download authorization and generic transfer integration, including cancellation/reconnect/revocation.
5. Tests: isolated two-peer Tor/MCP acceptance; recursive rejected with **zero listing data** followed by successful manual directory-by-directory LIST; hidden entries, changed policy/assignments, cursor exhaustion, aliases and topology moves; ASCII either-side preference; portable names including `CON`, `AUX`, `COM1`, percent and Unicode; no host OS/physical metadata leakage; huge directories, malformed hostile paths, invalid encodings, empty pages/cursors; export staging failure, cancellation, credit exemption, full-file hash and checkpoint resume.

**Stop at the read-only server contract.** Remote uploads, writable mutations, credits, browser UI, and queues are future explicitly approved milestones. Reuse current services and avoid broad backend rewrites to satisfy speculative server cases.
