# Read-only FileManager Backend

## 1. Purpose and integration

Implement `ReadOnlyFileManager`, a C++20 backend of the existing `IFileManager` (`file_manager.md`) for indexing and serving **externally managed** directories. It never writes to source trees. Instances and their private catalogs are application-wide: multiple DarkSpeak identities may mount one namespace without repeating scans or hashes. The backend contains no identity/contact models, permission rules, network code, or QML; it enforces generic host-supplied authorization and exclusion decisions. Use Qt, QCoro, `Result<T>`, the common async/limits/notification contracts, and the existing directory subscription API. Backend-specific configuration/diagnostics may be reached through the concrete type; common browsing uses `IFileManager` only.

Each source root is an independent `NamespaceId` with persisted UUID file/directory IDs and a private, versioned SQLite index outside the source root. Root/configuration/catalog identities are validated on reopening. A backend instance's root, symlink policy, and verification policy are explicit persisted settings. Root access is read-only even if OS permissions allow writes. `createFile`, `replaceFile`, `mkdir`, `rename`, `move`, `remove`, and pending-writer APIs return `UnsupportedCapability` as applicable. `list`, `lookup`, `stat`, `openRead`, `prepareRead`, `reconcile`, and notifications satisfy the common interface.

## 2. Index and stable identity

Store directory topology as `(directory_id, parent_id, name)` and file entries as `(file_id, parent_id, name, filesystem evidence, size, mtime, SHA-256/hash state, entry status, generation)`. Do not store descendant absolute paths as authoritative data. A recognized directory move/rename updates that node's parent/name in one transaction, not every descendant. IDs remain stable across recognized moves; content SHA-256 changes independently of entry identity.

For the first implementation, use filesystem/device identity plus inode where available as the primary move/rename hint. Inodes can be reused; confirm with available metadata and do not assume cross-filesystem identity. Optionally fingerprint a directory's immediate entries from a deterministic ordered encoding of `(name, type, size, mtime)` to support offline move recognition. Fingerprints are hints, not proof: identical copies must have distinct IDs, ambiguous matches get new IDs, and lookup order must not decide a conflict. Do not recursively hash contents to identify moved directories. No `.dirid`, manifests, or other metadata are written into source directories.

Retain indexed metadata for deleted/missing entries only as needed for bounded reconciliation/history; remove them from normal active listings once absence is established. External additions, modifications, moves and removals are expected and reconciled automatically. On detected change, mark an existing entry `EntryStatus::Updating`, retain its last known metadata for UI display, and block new reads/download preparations until revalidated. Normal listings include files and directories with `EntryStatus::Available` or `EntryStatus::Updating`, subject to requester authorization and exclusions; omit `Missing` and `Inconsistent`. Only `Available` files may be opened or prepared. Metadata browsing/subscriptions for an `Updating` directory remain possible. An authorized attempt to read an `Updating` file returns `Busy`; hidden/denied entries still appear absent. Emit generation-based notifications when state/metadata changes. A new file may appear with size/mtime before its hash exists; hash state is distinct from entry state.

### 2.1 Linux source names and deterministic encoding

Use the library's pure, global `encodeLinuxName(QByteArrayView)` for source-name encoding policy v1. Accept every nonempty Linux component of at most 255 raw bytes except NUL, `/`, and the special entries `.` and `..`. Preserve printable, valid UTF-8 characters, including spaces, punctuation and Linux-valid backslashes/colons. Preserve case and Unicode normalization exactly: `Report` and `report`, and canonically equivalent Unicode byte sequences, remain distinct entries. Do not apply the managed native backend's normalization, case folding, reserved-name rejection, or numeric collision suffixes to these names.

Encode literal `%` as `%25`; encode control/format characters (including tabs, newlines and bidi controls), Unicode line/paragraph separators, Unicode noncharacters, and invalid UTF-8 bytes as uppercase `%HH` sequences for their original bytes. Escape invalid sequences byte by byte without lossy Unicode conversion. This makes the mapping injective and independent of discovery order: `a<TAB>b` becomes `a%09b`, while literal `a%09b` becomes `a%2509b`. Encoded components may occupy up to 765 UTF-8 bytes; bound logical-path/SQL/cursor storage accordingly without truncating names. Persist the encoding policy and Unicode classification version; reject an unsupported version instead of silently changing mappings.

Keep original source component bytes separately and resolve them through anchored directory descriptors. Encoded labels are never URL-decoded to construct filesystem paths. They are filename components, not URLs: URL parsers, repeated percent decoding, HTML interpretation, case folding and normalization must not change their meaning. Use exact encoded-component matching and deterministic bytewise keys for lookup/pagination. UI rendering still escapes markup. The existing managed-native name policy remains separate.

### 2.2 Common metadata and capabilities

Use common `EntryStatus { Available = 0, Missing = 1, Inconsistent = 2, Updating = 3 }`, `HashState { Missing, Stale, Computing, Verified }`, and `NamespaceStatus { Updating, Ready, Failed }`. `FileInfo::hash_state` describes the digest independently of entry availability: a metadata-validated `Available` file may have `Missing` hash state and acquire a digest lazily during preparation. `Computing` indicates an admitted hash operation; cancellation/failure restores `Missing` or `Stale`. A retained digest for changed content is `Stale`, never `Verified`. Directory hashes remain `Missing`. `Verified` means a complete digest was previously calculated and its recorded source evidence is still valid under the configured verification mode; it is not a claim of immutability.

`NamespaceInfo` reports status, optional `readiness_error`, and common capability flags `Read`, `Write`, `PreparedRead`, `DirectorySubscriptions`, `SnapshotReads`, `ResumeLeases`. Advertise only implemented capabilities. The read-only backend omits `Write`. Root/configuration/exclusion validation must finish before any content is accessible. During startup scanning, effective entry status is `Updating` until each entry's evidence is revalidated (an epoch may avoid rewriting the entire catalog). Individually validated `Available` entries may be served while the namespace remains `Updating`; `Ready` means the initial discovery pass completed, not that every file was hashed. Failed/incomplete discovery reports its cause without presenting stale content as validated.

## 3. Discovery, freshness, and hashing

On open, load the private catalog promptly and start a bounded low-priority worker scan. A fast pass discovers topology and basic metadata, marks unvalidated or changed entries `Updating`, and commits batches without constructing the full tree in RAM. Use `QFileSystemWatcher` initially; watcher paths are hints only, and raw-byte, descriptor-relative enumeration remains authoritative (including invalid-UTF-8 names). Watchers may be limited or lost, so periodically reconcile and recover after restart. Use size and `mtime` as the initial change evidence; add stronger filesystem-specific checks later. File/directory metadata is refreshed on demand at interactive priority. Startup and background I/O must not block application startup or the UI; readiness and failures are reported per namespace, with stale/unverified entries not downloadable.

Only a successfully completed enumeration of a directory can establish absence of an indexed child. Cancellation, permission/I/O errors, watcher loss, catalog exhaustion and partial scans do not imply deletion. Preserve unvalidated entries as `Updating` and schedule bounded retries; never infer a move or removal from an incomplete scan. Device/inode evidence and directory fingerprints remain hints: uncertain identity continuity assigns a new ID and invalidates dependent VFS/authorization state instead of inheriting permissions by heuristic matching.

Enforce finite configured budgets for queued scan directories, per-turn entries, watches, concurrent scans/hashes, retries, catalog/history growth, cache pins, prepared readers and snapshot bytes/leases. Watch exhaustion falls back to bounded periodic reconciliation. Other exhaustion reports `QuotaExceeded`/`QueueFull` as appropriate, pauses discovery without deleting unseen entries, and preserves cleanup/recovery headroom. Source bytes are not backend-owned payload storage; index, staging and lease storage have explicit separate accounting. Large-directory tests configure an adequate finite entry/catalog budget rather than bypassing limits.

SHA-256 is lazy: do not hash the entire collection as a consequence of opening or scanning it. Cache hashes with their validated source metadata. A download preparation must obtain a valid SHA-256 **before any payload bytes are sent**; hash missing/stale files on demand at interactive priority. If the source changes during preparation, invalidate and retry within bounded limits or fail with a typed error. Announced hashes identify the expected content version; Cached/Rehash detect changes using their documented evidence and do not promise immutable source bytes. The recipient verifies the full SHA-256 before publication, including resumed transfers.

Configure one of three read-verification modes per backend instance:

- **Cached** (default): reuse a cached SHA-256 when size/mtime still match; validate identity and metadata before opening and detect changes when practical during/after reading.
- **Rehash**: hash the current source afresh before each transfer; transmit that hash before any data. A changed source during transfer still causes failure where detectable; the receiver's final hash is authoritative.
- **Snapshot**: copy the source into quota-limited private staging, write-lock the staged object against further modification by this backend (with restrictive OS permissions and additional platform protections where available), hash the completed staged bytes, then provide the hash and read **from the staged object**. A copy made during concurrent source modifications might not represent a coherent historical version, but the transmitted bytes must match the announced hash. Read-only permissions do not protect against privileged local processes; the guarantee covers the backend-controlled staged object, with external tampering detected where possible and final receiver verification mandatory.

`prepareRead` returns an already opened reader and the metadata/expected digest selected for that source object as one logical operation, never opening one path and later independently looking up another object for its digest. `PreparedRead::consistency` is `ReadConsistency::DetectChanges` for Cached/Rehash and `Snapshot` for an isolated staged copy. Cached/Rehash preserve opened-object identity and detect changes using bounded metadata checks, but an inode can be modified in place and unchanged size/mtime cannot prove unchanged content. These modes deliberately provide detection, not an immutable-version guarantee; undetected changes remain possible. Snapshot guarantees the announced digest describes the backend-controlled staged bytes, subject to the stated local-tampering limits. An existing `openRead` remains available for local access, but FileShare uses `prepareRead`. Implement bounded prepared-read/snapshot lifetimes and disk quotas. Interrupted transfers can retain a staged object under a private, expiring lease for resume; resume must bind to its original expected size/hash and never silently substitute changed source content. Crash cleanup is idempotent; never delete unrelated files. Rehashing before a transfer does not by itself ensure immutability while streaming.

### 3.1 Sender verification and transfer completion

The transfer layer must compute SHA-256 over the actual payload bytes read for a full sequential transfer, in file-offset order, using bounded worker chunks. Compare the digest and exact byte count with the prepared expected hash/size before sending a successful transfer-complete status. A mismatch, short file, detected metadata/identity change, cancellation or policy revocation sends a failed/error outcome and invalidates the affected cached hash; it must never be followed by successful completion for that attempt. A later matching metadata check or a hash of a fresh pathname cannot overrule a mismatch in the bytes actually sent. The receiver still verifies the entire expected file before publication.

Random access, duplicate/retransmitted chunks and resumed suffixes cannot simply be appended to the same SHA-256 stream and claimed to verify the complete file. Track logical offsets. For a sequential suffix resume, rebuild the hash prefix by rereading it from the same prepared reader before hashing the transmitted suffix; never trust persisted incremental checksum state. For arbitrary range scheduling, use bounded ordered verification of the complete prepared reader or an isolated snapshot, explicitly distinguish current-source verification from verification of earlier transmitted bytes, and retain mandatory receiver verification of the full reconstructed file. A failed or unavailable required verification fails the attempt; an incomplete digest is never evidence for successful completion. Transfer framing/status integration belongs to FileShare, not this storage backend.

## 4. Symlink resolution

Backend setting `SymlinkPolicy`: `Never` (default), `WithinVfs`, `Always`. `Never` does not traverse symlinks. `WithinVfs` permits resolution only if the final target is represented in the composed VFS **and** the requester can access that target; the composition/authorization layer supplies this check, because the backend is identity-agnostic. Cross-mount targets are resolved through VFS composition, not by guessing a physical-root boundary. `Always` follows independently accessible targets as `WithinVfs` does, and additionally permits final regular-file targets outside the assigned VFS only when the request's storage assignment explicitly enables external files. External directories always require independent VFS access. Resolve bounded chains to the final opened object; intermediate directory links may be used to reach an allowed file, but never become browsable through this exception. Both settings require a red warning that individual files outside the configured storage boundary can be exposed. The assignment capability is administrative, not a contact/group permission; missing evidence fails closed.

All modes validate names, bound link depth/recursion, detect cycles, resolve through race-resistant descriptor-relative operations where supported, and respect OS access controls. Directory symlink aliases retain distinct VFS entries but share resolved target identity; avoid scanning/indexing the same target recursively through aliases. Treat link/target changes as index changes. Unsafe resolution fails closed.

### 4.1 Host exclusions and object types

The host supplies a versioned exclusion set of **directory roots (including all descendants)** and **individual filesystem objects**, in addition to the backend's mandatory self-exclusions for its private catalog, staging, recovery, and metadata. DarkSpeak supplies private application, identity, and credential storage. Resolve configured exclusions to anchored filesystem locations and filesystem identities (device/filesystem identity + inode on Linux), retaining stable handles where supported; reject or quarantine an unsafe/unresolvable exclusion configuration rather than silently running with incomplete protection. Exclusion paths are configuration, not peer inputs. The host updates exclusions through a serialized backend operation that atomically publishes a new exclusion generation and invalidates affected listings, cached indexes, prepared readers, and in-flight access before the new policy is considered active.

Exclusions override **every** symlink policy, including `Always`. For each discovered or requested object, check the resolved object identity against excluded objects **and each traversed ancestor** against excluded directory roots, accounting for hard links, symlink chains, bind mounts, mount aliases, and other equivalent paths. Re-check at access time with anchored handles to avoid check/open races; do not accept lexical prefix checking or a cached allow decision alone. An excluded object is omitted from remotely visible listings; remote lookup/read errors must not distinguish it from an absent object. A hard link to an excluded file is excluded by the same underlying identity. A file's currently traversed ancestors do not reveal its other hard-link locations: reject/quarantine multiply linked files unless the backend can securely establish that their aliases do not reach excluded objects/subtrees, or the host supplies sufficient validated identity evidence. Do not claim that pathname ancestry alone enforces excluded-root privacy for hard links. If secure identity/ancestry checking is unavailable, the affected entry is inaccessible, even under `Always`. Newly added exclusions revoke access and terminate affected active reads safely (data already transmitted cannot be recalled). Changes to source paths, aliases, and excluded roots trigger invalidation/reconciliation.

Only regular files are readable/hashable and only directories are traversable; symlinks are resolved solely under the configured policy. Reject FIFOs, sockets, character/block devices, and other unsupported object types **before content I/O**, using safe no-follow type inspection and verification of the opened object's type to prevent replacement races. Never open a special file as a stream while attempting to classify it. Exclusions and type checks apply to scanning, hashing, snapshots, `prepareRead`, `openRead`, and cached catalog results. Only the final regular-file exception can waive assignment confinement under `Always`; exclusion/type checks never are.

### 4.2 Request-scoped target authorization

A `WithinVfs` link is visible/usable only when its resolved destination `(NamespaceId, FileId/DirectoryId)` is visible and accessible to the current user/contact for the requested operation. Once authorized, treat that destination like any other file/directory ID. Otherwise hide the link, including in directory listings, and report `MissingEntry` for direct lookup/stat/read without exposing the denied target's name, path or metadata. Access to the link does not independently grant access to a `WithinVfs` destination. `Always` uses the same destination checks, except for the explicitly permitted external regular-file case above; host exclusions still override it.

Use a small host-supplied callback carried by the current request, for example:

```cpp
enum class AccessOperation { Inspect, List, Read };
using EntryAccessCheck = std::function<Result<bool>(
    NamespaceId target_namespace, QUuid target_id, AccessOperation operation)>;
```

The VFS creates the callback by capturing the requester and its current authorization-policy generation; the backend does not learn identities or contacts. The composition layer resolves cross-mount destinations to IDs and delegates their actual operations through `IFileManager`. The callback checks those IDs using the ordinary authorization engine. Supply it explicitly in request-owned options/context for metadata, listing and read/preparation operations that can resolve aliases; do not install a mutable process-global/current-contact callback on a shared backend. Missing checks, errors, stale policy generations and unresolved targets fail closed for `WithinVfs` aliases. A trusted local administrative operation must opt into its own explicit context; absence of a callback is not implicit approval of an uncertain target.

The callback is bounded, thread-safe, nonblocking, and independent of UI object lifetimes; it uses current in-memory authorization state, not reentrant filesystem/catalog I/O. Bind approval to the opened target identity and revalidate on target/policy changes. Retain safe request state for active readers and stop them on revocation. Never store requester-specific allow results or filtered listing pages in the shared unfiltered index/cache. Filter before returning any entry metadata, totals or notifications; peer-facing cursors must not reveal hidden names, IDs or counts and must be invalidated when the requester's authorization generation changes. Detailed callback/options integration is part of the read-only/VFS implementation; no second abstract storage interface is introduced.

## 5. Directory subscriptions and caches

Implement common move-only RAII `DirectorySubscription` (`file_manager.md`). A successful subscription registers interest in one directory and pins its bounded per-directory metadata cache entry; move transfers ownership, destruction/reset unsubscribes without blocking. The backend persists changes irrespective of subscribers. With active observers, emit coalesced generation-aware directory/entry notifications on the registered Qt context; without observers, avoid detailed UI notifications. Directory deletion/invalidation and queue overflow deliver terminal/rescan indications. Never invoke callbacks after subscriber teardown; allow callbacks already running to finish safely under owned state.

Use a bounded per-directory LRU of parsed metadata/pages and optionally immutable snapshots. Unpinned least-recently-used entries are evicted first; pinning cannot retain unbounded file lists, and subscription/pin budgets prevent peer-driven memory growth. Paginate large directories from SQLite. Keep reference-counting and eviction local to the backend; no UI dependency. Short transactions, bounded scanning/hashing concurrency, cancellation, and low I/O priority preserve responsiveness.

Deliver the concrete backend, private versioned catalog and explicit rejection/reindexing of unsupported schemas, configuration and capability reporting, common-interface compatibility, and tests. Cover all common status/hash/readiness/capability transitions, deterministic Linux name encoding (literal escapes, invalid UTF-8, normalization/case distinctions and maximum expansion), partial-scan absence rules, sender payload verification/failure and resumed/range-read limits, request-scoped authorization isolation and hidden targets in listings, restart and offline move/rename, inode reuse/ambiguous fingerprints/identical directory copies, external changes while a reader is prepared, missing hashes and all verification modes, interrupted snapshot leases and quota/cleanup, watchers dropping events, symlink cycles/races/escape under each policy, host exclusions including hard links/bind mounts/aliases and live policy updates, special-file rejection before I/O, per-contact target authorization integration via VFS, reference-counted subscription moves/destruction, cache eviction with pins, million-entry paging, bounded scans, and UI-thread nonblocking behavior. Do not add separate abstract storage interfaces.
