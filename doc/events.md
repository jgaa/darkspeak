# Events journal

Events is optional and defaults **off**. Settings → Events controls recording and timestamp precision (exact seconds, 1 minute, 5 minutes, 30 minutes, or 1 hour; default 1 minute). Filename recording defaults **on**, independently of the Events switch, and can be disabled for future events. Save applies changes immediately, Cancel discards the draft. Enabling/disabling records a control event. Disabling always stops recording, even if storage failure prevents writing its marker.

The journal stores activity metadata only: local integer identity/contact references, bounded object IDs (including a digest of the public peer handle for linking unknown contact requests to their decisions), event kind, direction, outcome, and timestamps. It never copies messages, bios, notes, paths, addresses, avatars, media contents, or their content hashes. File offers and transfer events optionally include a basename, bounded to 255 UTF-8 bytes, without separators or control/format characters. Turning filename recording off does not remove names already recorded; clear events to remove the existing journal. Aggregation summaries never contain filenames. Identity/contact references are nullable and intentionally do not cascade on deletion. They may refer to records that no longer exist. Outgoing messages have a pending event when queued and a success event when submitted to the encrypted connection; a receipt is a separate event. Transfer events cover offers and started/completed/failed/rejected/cancelled transitions, not data chunks, byte progress, or individual acknowledgements. Avatar/profile/bio exchanges and automatic security rejections/limits are included. Successful handshakes, idle connections, keepalives, and arbitrary connection attempts are excluded.

## Persistence and chain format

`event_schema.version = 2` identifies the independently versioned journal extension. Its tables and indexes are installed transactionally on first use (enabling, viewing, verifying, or clearing), without rebuilding the profile or changing the existing application schema. `event` uses `INTEGER PRIMARY KEY AUTOINCREMENT`; `(identity,id)` and `(contact,id)` indexes support contextual access. The base event metadata version remains 1; a separate `hash_version` identifies canonical hash formats 1 and 2. The first-use upgrade adds nullable `filename` and `hash_version` columns in place, preserving all old rows, hashes, indexes and the integer sequence. Ordinary `repeat_count`, `window_start`, and `window_end` values are NULL.

Each row's SHA-256 covers its canonical content and the preceding row's hash. The first row uses 32 zero bytes as its predecessor. Serialization is Qt QDataStream version Qt_6_0, big endian: byte array domain `DarkSpeak event chain v1`; predecessor byte array; signed 64-bit id, version, timestamp, precision, kind, direction, outcome; identity then contact as presence bool and signed 64-bit value (zero for NULL); bounded object ID byte array (canonical empty, never a null array); repeat_count, window_start, window_end each as presence bool and signed 64-bit value. New rows use hash format 2: the domain is `DarkSpeak event chain v2`, followed by the same fields and then the filename presence bool and its UTF-8 byte array (canonical empty for NULL). Format-1 rows must have a NULL filename. The fixed regression fixtures in `tests/event_journal_test.cpp` anchors this format. Closed rows and summary rows are immutable; insert + finalizing its hash happen in one savepoint before commit.

Check chain verifies 100 rows per event-loop turn up to a captured tail ID, keeping the UI responsive. It reports the verified prefix. This is an internal consistency check: it does not prove authenticity against full chain recomputation, tail truncation, rollback to a backup, or an attacker able to rewrite all local state.

Clear events requires confirmation, atomically removes rows and inserts a new `Cleared` genesis row, including when recording is off. The integer sequence is not reset. Pending aggregate counters are discarded so old activity cannot leak into the new chain. Existing events otherwise remain until cleared; disabling does not delete them. Clearing is a logical database operation, not a promise to erase backups or filesystem snapshots.

## Resource bounds

Local identity lifecycle actions bypass remote activity limits so hostile traffic cannot crowd them out (the disk ceiling still applies). A monotonic global token bucket allows 120 immediate activity rows, refilling at two rows/second. Each similarity bucket allows 20 immediate rows and refills one token per 30 seconds. Keys include only fixed event enums and locally resolved identity/contact IDs, not object IDs or peer strings. At most 256 buckets plus one overflow bucket exist. A fixed per-connection context cache avoids database lookups for each suppressed peer event. Saturating 64-bit counters retain suppressed counts. Idle buckets can be reclaimed after 30 minutes when new traffic needs space.

A single-shot timer appends summaries after 30 minutes, also flushing on precision changes, disabling, and orderly shutdown. A summary stores its suppressed count and rounded start/end in its own columns; overflowing distinct keys becomes a generic summary without invented contact attribution. At most 257 summaries are generated per interval, in one transaction to avoid hundreds of disk syncs; failed batches retain their counters. Counters held in memory can be lost on a crash. Raw timestamps for summaries are never persisted; the configured upward rounding applies to timestamps and both summary endpoints.

The journal stops activity writes at 499,999 rows and reserves the 500,000th row for a disable marker. It reports that the journal is full and preserves existing records. Clear events frees the logical budget. This bounds indefinite attacker-driven growth as well as CPU, write frequency, and memory. Database errors remain visible on Events; logging failures do not reject or alter messenger operations. Enabling fails visibly if the journal cannot be opened; Settings restores its draft's persisted values. No new threads, timers while idle without pending work, dependencies, or external services are required.

The UI retains at most 100 rows, uses keyset pagination by ID, and coalesces live refreshes. Wide layouts show list and details together; narrow layouts replace the list with details and provide a Back icon. Metadata is plain text and details can be selected/copied. All visible strings are localization-ready.

## MCP review

The repository has no MCP server or existing event tools. No new external API or MCP exposure is added; any future event export/tool needs explicit approval because it reveals activity metadata.
