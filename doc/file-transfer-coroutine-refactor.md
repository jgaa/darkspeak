# Codex instruction: replace distributed file-transfer orchestration

**Owner-approved direction.** Refactor the **generic transfer execution architecture**, not the protocol or future FileShare features. The current branch has no single owner: `File`, `Contact`, `Peer`, channels, timeout callbacks and independently started coroutines can each advance/terminate an attempt. This created interacting state machines, reentrancy flags, polling, duplicated cleanup and repeated concurrency fixes. **Stop patching that architecture. Replace it with a structured, coroutine-owned transfer attempt.**

## Required design

- **One active-attempt owner per transfer and direction:** a `TransferSession` or equivalent C++ object with one root coroutine for each running attempt. Child coroutines are **awaited or explicitly joined**; no detached operation can mutate this attempt after owner termination. The owner exclusively decides execution-phase transitions, outcome and durable lifecycle commands. A restart/reconnect creates a new attempt/session from authoritative persisted recovery state; durable transfer identity remains stable.
- The coroutine expresses the workflow: admission/authorization → source/receiver preparation → checkpoint selection and mutual validation → bounded chunk transfer and checkpoint confirmation → final SHA-256 verification → atomic receiver publication and completion → cleanup. Separate sender/receiver subroutines are fine; keep common policy and resource rules generic. Never transmit file data before required journal/negotiation validation.
- `Peer` handles authenticated wire parsing and routes **bounded, validated, attempt-scoped events** to the session; it never owns transfer completion or invokes independent transfer-state mutations. `Contact` handles identity/policy, admission, shared **application-wide transfer manager** and contact limits; UI/MCP `File` actions submit commands to the session/manager. `IFileManager` handles readers/writers, hashing, durable journal and publication; it does not independently orchestrate network transfers. The `File` model is a projection of authoritative state, not another controller. A **single application-wide transfer manager with feature-specific controllers** owns admission/queueing; do not create FileShare-specific transport or scheduler.
- Give the session exclusive lifecycle ownership of reservation tokens, cancellation, deadline, reader/writer leases and in-flight child tasks. Enforce the existing **two active transfers per contact**, the transfer-window/checkpoint backpressure and resource budgets. Use event-driven awaiting/signaling rather than polling (especially `preparing_initial_offer` / 25 ms timer loops). Only the owner writes the authoritative attempt outcome; synchronization and immediate admission barriers still guard publication, revocation and cancellation races.
- All external events (wire messages, disconnection, timeout, user cancel/pause/resume, source changes, authorization withdrawal) are **commands/events**, not independent writers to the running attempt. Validate and enqueue with bounded memory/time. Revocation must synchronously stop further admissions/writes at the security boundary, then notify the owner for coordinated cleanup; never delay revocation until the coroutine next wakes.
- One deterministic cleanup/finalization path: stop new work; cancel and join outstanding operations; settle/record required durable evidence; release resources; notify the model. Cancellation before publication prevents publication; cancellation after a committed publication cannot undo committed content. Exactly one terminal outcome per attempt, with idempotent restart reconciliation. Connection loss preserves recoverable partial content; explicit cancellation and durable pause/failure remain distinguishable.
- Keep the **existing v3 wire protocol**, checkpoint interval/nonce rules, protobuf messages, integrity and security semantics, and current transfer-progress journal/fixtures wherever correct. No compatibility fallback, no legacy clients. Do not introduce new wire messages, storage schema versions, MCP tools or protocol features unless a concrete correctness impossibility is demonstrated and the owner approves it **before implementation**.
- Resume is sender-selected from a genuinely mutually confirmed durable SHA-256 prefix. Receiver checks its retained bytes; sender checks source bytes. Final full-file hash is mandatory before publication. Preserve bounded windows, typed errors, source-failure provenance, immutable transfer IDs/content, authentication and authorization rechecks. The journal is authoritative; application transfer history/UI is recoverable derived state. FileShare credits and upload coordination remain **outside** the generic engine and outside this task.
- Preserve required completion/replay correctness, but do not invent additional automatic recovery paths to handle speculative timing combinations. A safe interruption/explicit resume is preferable to new autonomous retry machinery unless the current spec explicitly requires automatic recovery.

## Execution: controlled migration, not another open-ended project

1. **Inspect narrowly:** identify the smallest set of entry points/state writers and define the new session boundary, event ownership, journal interface and cancellation ordering. Summarize the mapping of old owners to new owners before major edits. Consult `specs/protocol.md` (relevant transfer section), storage/checkpoint APIs and tests; do not recursively load all specs.
2. **Implement one owning session framework** with bounded routing, explicit phases and structured cancellation; move incoming and outgoing transfer orchestration to it in manageable increments. Preserve functioning storage/hash/wire helpers and security validation; do **not** rewrite them merely because they belong to the old flow.
3. **Retire displaced machinery** once callers use the owner: competing state-changing callbacks, redundant `PendingResume`/request phase state, polling, reentrancy flags and handoff bookkeeping. Remove dead code and outdated tests that test the discarded architecture rather than its required behavior. Do not delete security checks or regression coverage of required externally observable outcomes.
4. **Test existing guarantees** with focused unit and paired authenticated transfer tests: offer/accept; normal/empty transfers; flow and checkpoint backpressure; interruption/reconnect/resume; corrupted/changed source; malformed/old-attempt controls; authorization withdrawal; cancellation before/during/after publication; durable crash/restart; completed EOF reconciliation; balanced reservations on every exit. Prefer deterministic controlled events, not repeated sleeps or exhaustive permutations.
5. **Release gate:** enable mandatory checkpoint advertisement in production, exercise one real application-to-application file transfer and restart/resume, run the agreed relevant suites, and report remaining known deviations. Do not call the milestone finished while production transfers are disabled. Follow `agents.md` build restrictions; request the owner's full-build step if required.

## Boundaries, decisions and reporting

- **No scope growth without owner approval.** A newly found defect inside a listed invariant may be corrected within that task; additional features, unrelated hardening, migration, new compatibility paths, speculative recovery behaviors and extra test matrices require permission. Do not move the gate after tests pass.
- **No wasted refactoring:** minimal API disruption, no second transfer implementation left running beside the old one, no feature or policy logic in QML. No FileShare credits, upload coordinator, browser, dashboard or metrics work in this milestone.
- **Terminal journal retention policy is an owner decision**; protect evidence needed for active recovery now, but do not invent compaction/expiry rules or block the coroutine architecture on downstream credit retention.
- Update `doc/file-transfer-implementation.md` using checked Markdown tasks. Check off only after implementation/test evidence; don't append a running diary. State the current blocker and next finite step. Stop and seek a decision where a fundamental protocol or durability change is genuinely unavoidable.

**Success is reduced independent mutable state, one lifecycle owner, correct transfers and a working production path—not maximum recovery features, maximum test count, or merely fewer source lines.**
